# Static GitHub Pages Remake

The project is pivoting from hosted Python/SQLite deployment to a static GitHub
Pages dashboard generated by GitHub Actions.

Reason: the hosted backend path adds authentication, reverse proxy, persistent
disk, backups, restore drills, and operational maintenance. The desired beta is
better served by committed inputs, generated static data, and Pages hosting.

## Target Architecture

- GitHub Pages serves the public app.
- GitHub Actions runs scheduled/manual data generation.
- Curated inputs live in reviewed YAML files under `data/`.
- Generated endpoint-like JSON is committed under `docs/data/`.
- Browser code reads static JSON in Pages mode and `/api/*` in local mode.
- Public JavaScript remains token-free and read-only.
- Git history provides auditability and rollback for both curated inputs and
  generated data.

## Source Inputs

Current static source files:

```text
data/watchlist.yml
data/manual_consensus.yml
data/peer_groups.yml
data/sector_kpis.yml
data/manual_events.yml
data/quarterly_statement_reviews.yml
```

These files hold watchlist membership, notes, peer groups, manual/source rows,
events, sector KPI inputs, and review status. YAML is used because it is easier
to review than JSON. `scripts/validate_static_inputs.py` validates YAML quickly;
the static builder validates again before publishing generated JSON.

## Generated Outputs

Core generated files:

```text
docs/data/manifest.json
docs/data/watchlist.json
docs/data/watchlist-overview.json
docs/data/fundamentals-watchlist.json
docs/data/fundamentals-all.json
docs/data/technical-indicators-watchlist.json
docs/data/technical-indicators-all.json
docs/data/events.json
docs/data/sources.json
docs/data/consensus.json
docs/data/benchmarks/*.json
```

`manifest.json` should report mode, generation time, input files, output files,
watchlist count, source status, refresh request state, edit policy, and
limitations.

## Scheduling

The workflow currently supports scheduled and manual generation. Desired
operator meaning:

- weekday pre-open refresh
- weekday evening/post-close refresh
- one Saturday refresh
- one Sunday refresh
- manual dispatch for operator-triggered refresh

GitHub schedule timing is best-effort and UTC-based. The UI should show "last
generated" and source status, not imply live market infrastructure.

## Editing Policy

Static Pages cannot safely write to the repo by itself. Avoid:

- browser-side GitHub tokens
- direct repo writes from public JavaScript
- OAuth/GitHub App write flows for the first beta
- serverless write proxies

Default workflow:

1. Edit `data/*.yml` on a branch.
2. Validate schema with `python3 scripts/validate_static_inputs.py`.
3. Regenerate static JSON.
4. Open/merge a PR.
5. Run or observe the static-data workflow.
6. Verify public Pages, manifest timestamp, and affected rows.

See `docs/watchlist-edit-workflow.md` for the current watchlist and peer-group
edit procedure.

## Feature Mapping

Keep in static mode:

- Beta label and screening-grade warning.
- Watchlist synthesis view.
- Fundamentals, own history, technical indicators, benchmarks, News/Events,
  Sources, and separate RSI14 screener tab.
- Source-gated displayed multiples and raw-provider audit fields.
- Explicit missing technical coverage rows.
- Peer group curation status and sector benchmark components.
- NewsWeb/event rows with source links, freshness, confidence, and limitations.
- No recommendation logic or standalone valuation labels.

Reduce in static mode:

- Live refresh buttons become generated-data status and workflow guidance.
- SQLite-backed edits become repo-file edits or draft/export helpers.
- On-demand NewsWeb for public shared data becomes scheduled/manual generated
  data.
- Hosted Basic Auth, backup, restore, Caddy, and systemd support become legacy
  backend references.
