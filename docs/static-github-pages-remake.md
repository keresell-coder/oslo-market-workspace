# Static GitHub Pages Remake Plan

This project is pivoting away from hosted Python/SQLite deployment toward a
static GitHub Pages screening dashboard generated by GitHub Actions.

Reason: the Python/SQLite app became a small hosted backend product. That adds
hosting, authentication, persistent disk, backup, restore, and maintenance work
that is out of proportion to the desired beta experience. The RSI14 Screener
already proves the lower-maintenance model: scheduled GitHub Actions generate
static data, and GitHub Pages serves it.

## Target Shape

- GitHub Pages serves the public app.
- GitHub Actions runs the data build on a schedule and manual dispatch.
- Generated JSON/CSV artifacts are committed to, or published with, the Pages
  output.
- The browser reads static JSON files instead of calling `/api/*` endpoints.
- No always-on Python server.
- No hosted SQLite.
- No hosted Basic Auth, reverse proxy, systemd service, or database backup job.
- The app remains descriptive and screening-grade.

## Data Inputs

Move editable/runtime state out of SQLite and into reviewed repo files:

```text
data/watchlist.yml
data/manual_consensus.yml
data/peer_groups.yml
data/sector_kpis.yml
data/manual_events.yml
data/quarterly_statement_reviews.yml
```

These files become the source of truth for watchlist membership, notes, curated
peer groups, manual/source-reviewed rows, and review status. Missing data stays
missing.

## Generated Outputs

A static build script should generate files such as:

```text
site/data/manifest.json
site/data/watchlist-overview.json
site/data/fundamentals.json
site/data/own-history.json
site/data/technical-indicators.json
site/data/benchmarks.json
site/data/events.json
site/data/sources.json
```

`manifest.json` should include generation time, source timestamps, workflow run
metadata, source errors, and stale/missing-data status.

## Scheduling

Recommended first schedule:

- weekday pre-open run, around 07:30 Europe/Oslo
- weekday post-close/evening run, around 18:30 Europe/Oslo
- manual `workflow_dispatch` run for operator-triggered refreshes

GitHub Actions schedules can be delayed and should not be treated as exact
market infrastructure. The UI should say "last generated" and show source
freshness/error states rather than promising live data.

## News And Events

True on-demand NewsWeb search from GitHub Pages is not a good fit because it
would run from each user's browser, expose rate-limit/CORS issues, and would not
create a reviewed shared result.

Preferred static approach:

- scheduled Actions fetch NewsWeb rows for the current watchlist
- store latest rows and a 24-hour digest in `site/data/events.json`
- include per-symbol fetch status, source URL, fetched time, duplicate/correction
  grouping, stale/error states, and limitations
- add manual dispatch for an operator "refresh now" run from GitHub Actions

Optional later approach if truly needed:

- add an in-app link to NewsWeb ticker searches for ad hoc user lookup
- keep results outside the shared dataset unless entered into repo files and
  regenerated by Actions

## Watchlist Editing Options

A static GitHub Pages app cannot safely update repo files by itself unless the
user authenticates with GitHub and grants a token with repository write access.
Do not put a personal access token or write token into public JavaScript.

Recommended first implementation:

1. The visible app lets the user draft watchlist edits in the browser.
2. The app validates symbols and shows the resulting `watchlist.yml` diff or
   replacement content.
3. The user commits the change through GitHub's normal web editor or opens a PR.
4. The next scheduled/manual Action run generates updated static data.

Lowest-complexity variant:

- remove in-app persistence for watchlist edits
- add an "Edit watchlist source" link to `data/watchlist.yml` in GitHub
- rely on GitHub's web editor and manual/scheduled Actions

Possible later variant:

- app prepares a GitHub issue or pull-request link containing the proposed
  watchlist change
- an Action can process trusted operator-approved changes
- this adds complexity and must be designed carefully to avoid accepting
  untrusted issue text as executable instructions

Avoid for the first static remake:

- browser-side GitHub token storage
- direct repo writes from public Pages JavaScript
- GitHub OAuth/GitHub App write flow
- serverless write proxy

Those reintroduce auth/security/backend complexity.

## Feature Mapping

Keep:

- Beta v0.1.0 label and screening-grade warning
- Watchlist synthesis view
- RSI14 dashboard link/embed and `latest.csv` parsing
- technical indicators from `latest.csv`
- yfinance fundamentals snapshots generated by Actions
- descriptive price/own-history context from generated snapshots
- peer context from reviewed repo files
- consensus/source rows from reviewed repo files
- NewsWeb scheduled digest and source links
- source, timestamp, confidence, limitations, and missing-data visibility
- no recommendation logic and no standalone cheap/expensive/fair/neutral labels

Reduce or remove:

- live refresh buttons become "latest generated" status plus link to manual
  GitHub Action run
- SQLite-backed add/edit/delete flows become repo-file edits or draft/export UI
- on-demand NewsWeb rows become scheduled/manual Action generated data
- backup/restore scripts become less central because git history is the audit
  trail for curated inputs and generated data can be rebuilt
- Basic Auth and hosted verification scripts become out of scope for Pages

## First Static Remake Sprint

Goal: build a read-only GitHub Pages static version that preserves the main
screening information without SQLite or a running backend.

Tasks:

1. Create repo input files under `data/` for watchlist, peer groups, manual
   consensus/source rows, sector KPI rows, manual events, and quarterly review
   status.
2. Add `scripts/build_static_site_data.py` that reuses safe parsing/fetching
   logic from `app/server.py` but writes static JSON outputs.
3. Add a GitHub Actions workflow for weekday pre-open, weekday post-close, and
   manual dispatch generation.
4. Adapt the frontend to load `site/data/*.json` instead of `/api/*` for the
   static Pages mode.
5. Replace refresh buttons with generation status and links to source files or
   manual workflow run instructions.
6. Publish through GitHub Pages.
7. Verify the Pages URL from another device.

## Open Decisions

These should be confirmed before implementation:

- Should the GitHub Pages site be public, accepting that the watchlist and notes
  are public too?
- Should generated JSON be committed to the repo or uploaded as the Pages build
  artifact only?
- Should watchlist editing start as a GitHub web-editor link, or should the app
  include a draft/export diff helper in the first sprint?
- Should schedules run weekdays only, or also once on weekends for stale-state
  visibility?
- Which watchlist file format is preferred: YAML for human editing or JSON for
  simpler browser tooling?
